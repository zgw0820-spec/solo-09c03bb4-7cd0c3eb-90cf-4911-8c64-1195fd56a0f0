# UPS 安全停机演练台

机房断电后，用这套小工具判断 **UPS 剩余电量能否撑到共享存储等设备安全停机**，
并把推演过程变成可以一步一步点着走的演练。

* 后端：FastAPI（纯 Python 标准库 + FastAPI/Pydantic），排程器为精确枚举，无外部依赖服务
* 前端：原生 HTML/CSS/JS 单页，无构建步骤，深色机房风格
* 部署：Docker Compose 一条命令启动

---

## 快速开始（Docker Compose）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

改端口：`DRILL_PORT=8080 docker compose up --build`。

### 本地直接跑（不用 Docker）

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
# 打开 http://127.0.0.1:8000
```

跑测试：

```bash
pip install -r requirements-dev.txt
pytest -q
```

## 业务规则（与演习口径一一对应）

| 规则 | 实现 |
| --- | --- |
| 最多 6 台设备 | 录入表与后端校验均为 1–6 台 |
| 录入功率、停机耗时（整分钟）、依赖关系 | 表单逐台录入；耗时按整数分钟 |
| 设备停妥前按录入功率耗电 | 排队等待和正在停机的设备都按满功率计耗电，停妥后归零 |
| 同时最多 2 台正在停机 | 排程与演练全程校验，已下达命令也不越过 |
| 使用方全部停妥后才能停被依赖的设备 | 依赖按“我依赖谁”录入，被依赖方（如共享存储）最后停 |
| 给出余电够用且全部设备最早停妥的时序 | 精确枚举所有合法排程，先按完工时刻、再按耗电、再按稳定顺序取最优 |
| 可逐步演练并查看余电 | `+1 分钟` / `到下一事件` / `推进至结束`，实时余电、功率、曲线、逐分钟记录 |
| 余电不够时显示最小缺口 | 返回 `shortfall_wh` 与“至少需要”电量，并暂停推进（HTTP 409） |
| 补录余电后推进 | 补录后重新判定；够用即可继续，仍不足则继续显示新缺口 |
| 补录时保留已下达命令的完成时刻 | 已开始（`start ≤ 当前分钟`）的设备完全冻结，只重排尚未开始的动作 |

### 依赖方向说明

界面里“依赖设备”一列填写的是 **本机需要等待谁先停妥**。
例如样例：

```
Web 应用服务器 ─┐
业务应用服务器 ─┴→ 数据库服务器 ─┐
备份服务器 ──────────────────────┴→ 共享存储
```

也就是 `web.depends_on = [db]`，`db.depends_on = [storage]`，
因此 Web/业务先停，数据库与备份随后，共享存储最后停。

### 目标函数的取法

“最早停妥”优先于“最省电”：只要余电够，就选完工最早的那条时序；
余电不够时，给出的参考方案取“最省电”的时序，并报告相对它的最小缺口。
补录余电后，冻结已下达命令，重新在剩余设备上求最优。

排程器对 `n ≤ 6` 的所有合法排程（含主动空闲等待）做完全枚举，
并用“2 台并行 + 依赖约束”的暴力搜索在测试中交叉验证过最优性（见 `tests/test_planner.py`）。

## 样例场景（`GET /api/sample`）

| 设备 | 功率 | 停机耗时 | 依赖 |
| --- | --- | --- | --- |
| Web 应用服务器 | 450 W | 3 分钟 | 数据库服务器 |
| 业务应用服务器 | 420 W | 3 分钟 | 数据库服务器 |
| 数据库服务器 | 600 W | 4 分钟 | 共享存储 |
| 备份服务器 | 300 W | 2 分钟 | 共享存储 |
| 共享存储 | 800 W | 5 分钟 | — |

* 余电 **320 Wh**：12 分钟全部停妥，需要 **298.5 Wh**，还剩 **21.5 Wh**（够用）
* 余电 **250 Wh**：最小缺口 **48.5 Wh**，演练暂停，补录到 ≥ 298.5 Wh 才能推进

## 演练流程

1. **载入样例**（或手工录入设备），点“预览排程”看到甘特图、需要电量与结论。
2. 点“开始演练”，进入第 0 分钟。
3. 用 `+1 分钟`、`到下一事件`、`推进至结束` 推进；右侧设备卡片显示未开始/停机中/已停妥，
   余电卡与曲线同步下降，底部记录每分钟余电与实时功率。
4. 值班员核对 UPS 读数后，在“补录当前余电”里填实际值：
   * 已开始停机的设备保留原开始/停妥时刻；
   * 尚未开始的动作会被重新排程，界面列出“谁被移动了”；
   * 若仍不够，继续显示最小缺口，推进按钮保持禁用。
5. 全部停妥后显示最终剩余电量。

每次补录、推进都会写入右侧“事件”列表，便于复盘。

## API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/sample` | 内置样例 + 预期结果 |
| GET | `/api/health` | 健康检查（Compose healthcheck 使用） |
| POST | `/api/preview` | 用当前录入直接出方案，不创建会话 |
| POST | `/api/drills` | 创建演练会话，返回完整初始状态 |
| GET | `/api/drills/{id}` | 读取会话当前状态 |
| POST | `/api/drills/{id}/advance` | `{minutes}` 或 `{to_next_event: true}` 推进 |
| POST | `/api/drills/{id}/revise` | `{residual_wh}` 补录余电并重排未开始动作 |
| DELETE | `/api/drills/{id}` | 删除会话 |

缺电时 `advance` 返回 **409**，`detail` 里带最小缺口，前端据此禁用按钮并提示补录。

会话保存在进程内存（最多 200 个，LRU 淘汰），重启即清空，适合演练演示而非持久台账。

## 已知边界

* 会话在单进程内存中；多副本部署需要把状态外置（如 Redis/SQLite），当前 Compose 只起一个实例。
* 演练时钟按整分钟推进，功率按常量计；不支持有功功率曲线或电池放电曲线。
* 依赖关系在演练中不可修改（补录只改余电），需要改设备请重新开始一次演练。
